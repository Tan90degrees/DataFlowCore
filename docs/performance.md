# 业务性能验证

## 0.5.0 算子配置与公平准入

本版本移除新任务的 CPU/内存/并发开关，采用资源回填、按文件资源份额公平和老请求
保护。以下为 2026-10-14 本机 Python 3.14.8t、GIL 关闭、SQLite 的完整六节点入库业务。
2048 字符文件、HTTP 测试服务每请求等待 10ms、每块并行度 4，2 个执行器各固定 4 个
常驻槽位，0.1 秒心跳。每次使用新数据库和输入目录，包含提交、排队与查询耗时。

| 指标 | 24 文件，三轮中位数 | 120 文件，单轮预算压力 |
| --- | ---: | ---: |
| 每执行器声明预算 | CPU 8 / 2048 MiB | CPU 2 / 1024 MiB |
| 总耗时 | 0.597 秒 | 2.767 秒 |
| 吞吐 | 40.23 文件/秒 | 43.36 文件/秒 |
| 成功 / 尝试数 | 24 / 24 | 120 / 120 |
| 校验索引行数 | 120 | 600 |
| 使用的常驻进程 | 8 | 8 |

三轮 24 文件各有 16 个任务复用已执行过文件的槽位。120 文件压力中，共享预留峰值
为 CPU 2 / 640 MiB，未超过单执行器预算；文件放置门槛为 CPU 1 / 128 MiB，本次
Attempt 预留峰值最高 CPU 2 / 256 MiB，体现分支并行峰值与单算子放置门槛的区别。
节点资源等待时间按每文件合计的 P95 为 0.162 秒，产物 SHA256、GIL 状态和索引行数
均校验通过。每份报告新增 scheduler_policy 和 attempt_resource_peaks；只有算子
资源的公开配置也纳入断言。原始数据见 [fair-scheduling/summary.json](benchmarks/fair-scheduling/summary.json)。

上述负载用于验证完整业务与预算压力，老请求超过阈值后的行为另由持续小请求回归
确定性验证：阈值前允许回填，阈值后保护大节点，已有占用释放后大节点先获资源。
同套回归验证大内存队头回填、低占用文件优先、实际池宽度、取消和进程故障回收。
PostgreSQL 与真实 kind Pod 故障在 CI 验证，报告作为 workflow 附件。

这是测试向量服务负载；不同预算两列不是性能提升对比，也不把旧版本的加速比例用于
本轮公平策略。资源声明是准入预算，实际 RSS 和 Pod/cgroup 限额另行观测，生产模型
和存储必须实测。复现命令：

```bash
python scripts/business_benchmark.py --files 24 --workers 2 --slots 4 --chars 2048 \
  --interval .1 --output /tmp/business.json
python scripts/business_benchmark.py --files 120 --workers 2 --slots 4 --chars 2048 \
  --interval .1 --worker-cpu 2 --worker-memory-mb 1024 --output /tmp/batch-120.json
```

## 0.4.0 算子级调度

同一版本比较显式 `scheduling=task` 与默认 `operator`，固定一个执行器、4 个常驻槽位、
CPU 2 / 内存 1024 MiB 的声明预算。每轮 8 个 8192 字符文件，完整六节点文档入库 DAG，
HTTP 向量测试服务每请求等待 30ms，按 4 个页块并发调用。任务模式整段预留 CPU 2，
算子模式在 IO 阶段释放大部分 CPU，仍保持每文件完整 DAG 在同一常驻进程内执行。

2026-10-13 本机 Python 3.14.8t、GIL 关闭、SQLite，三轮交错顺序的中位数：

| 指标 | 任务预留 | 算子预留 |
| --- | ---: | ---: |
| 8 个文件总耗时 | 1.917 秒 | 0.771 秒 |
| 文件吞吐 | 4.17 / 秒 | 10.38 / 秒 |
| HTTP 并发峰值 | 4 | 16 |
| 使用的常驻进程 | 1 | 4 |
| 成功 / 尝试 / 索引行数 | 8 / 8 / 136 | 8 / 8 / 136 |

吞吐比为 2.49。两组都预建 4 个槽位，算子模式让原先因整任务预算而空闲的槽位参与；
没有临时新增进程。三轮算子模式预留 CPU 峰值均为 2、内存峰值均为 640 MiB，未超过
预算，逐文件产物哈希与索引数校验通过。原始数据和环境信息见
[operators/summary.json](benchmarks/operators/summary.json) 与同目录的 6 次报告。

这是声明预算下的 HTTP 等待负载；执行器声明并非实际 cgroup CPU 限额，向量服务为
确定性测试模型。不要把该比例外推到纯 CPU、真实模型或生产存储。CPU 核心收益是
避免超额准入与约束内部 map 并行；继续用实际业务测试合适的资源声明、池大小和槽位。
CI 另跑 PostgreSQL 全链路比较，并校验资源峰值，不设置易受机器波动影响的速度门槛。

```bash
python scripts/benchmark_operator_scheduling.py --repetitions 3
```

## 0.3.0 常驻进程改造

本节是新增实验，下方既有数据属于 0.2.0 及此前基线。改造前固定为 Git 提交
`2f37f717552f3cb8c68108f8b391282d577158e8`。同一机器、Python 3.14t、SQLite、新数据库，
24 个 2048 字符文件、2 执行器 × 4 槽位、0.1 秒心跳、HTTP 测试向量服务 0.01 秒等待。
三轮交错运行，全部文件成功且每文件仅一次尝试，校验全部输出 SHA256 与索引行数。

| 指标（三轮中位数） | 每任务新进程 | 常驻槽位 |
| --- | ---: | ---: |
| 24 文件耗时 | 1.272 s | 0.591 s |
| 吞吐 | 18.86 文件/s | 40.62 文件/s |
| 实际处理文件的运行进程数 | 24 | 8 |
| 使用已处理过文件的进程的任务数 | 0 | 16 |
| 成功文件 / 尝试数 | 24 / 24 | 24 / 24 |

本实验吞吐比为 **2.15 倍**，主要用于验证短任务的启动开销与进程复用。测试向量服务
不是生产 OCR/Embedding 模型，不能将上述吞吐用于生产容量推算。没有设置机器无关的
提速门槛；不同 CPU、存储、数据库、文件和模型负载的收益需要重测。
常驻进程 RSS 是生命周期峰值，CPU 是每任务增量，不能将峰值 RSS 逐任务求和。

原始三轮记录与源码摘要见 [resident](benchmarks/resident/summary.json)，复现命令：

```bash
python scripts/benchmark_resident.py
```

测量日期：2026-10-09。完整业务与故障矩阵见 [业务验收](business-validation.md)。
本报告测量编排、线程并行和流式数据处理；HTTP向量服务是确定性测试模型，
不代表实际OCR/VLM/Embedding模型的吞吐或精度。

## 环境与方法

- Linux x86_64，CPython 3.14.8t，运行时GIL关闭；可见9个逻辑CPU，cgroup配额8核。
- 本机状态库SQLite；独立管控、执行器、任务子进程以及真实HTTP测试服务。
  PostgreSQL和三节点K8S在CI另行验证，CI的原始性能数据作为business-performance附件。
- 基线为Git提交e1fe96e（0.1.0）。只给旧Context添加等效有界map适配，以运行同一
  业务算子；旧调度、进度刷盘、API、数据库和看门狗保持原提交实现。
- 改进版为0.2.0。每文件8192字符，固定512字符窗口、32字符重叠、4个向量线程，
  HTTP每请求等待10ms，24文件、1执行器、4槽位、轮询间隔0.5秒。
- 主对比与CPU对比各3轮，取中位数；多执行器、120文件及大文件是单轮补充验证。
  基准顺序执行，未隔离宿主其他负载；分位数采用经验下分位数，低样本只是近似值。
- 计时从生成输入/提交首任务到取得全部结果，包含排队、业务及客户端轮询，
  不包含集群启动。完成后另外校验索引总行数及所有产物SHA256。
- 每份JSON保留配置、Python/CPU配额、时间、源码摘要、API延迟、重试次数、
  CPU时间和RSS。未知指标使用null，基线没有步骤时长/RSS统计。

## 同负载改进前后

| 指标（三轮中位数） | 基线 | 改进版 |
|---|---:|---:|
| 24文件耗时 | 12.88 s | 3.80 s |
| 文件吞吐 | 1.86 文件/s | 6.32 文件/s |
| 排队P95 | 11.23 s | 3.13 s |
| 状态轮询请求 | 2388 | 70 |

业务吞吐提升 **3.39倍**。主要改善来自每轮填充可用槽位、合并
进度落盘，以及批量状态查询。改进版另有24次结果详情查询；上表不是整个系统的
HTTP请求总数。基线GET返回完整记录，批量状态返回摘要，不直接比较二者单请求时延。

## 单文件CPU线程并行

同一个文件、同一个任务进程，69个块，每块执行15000轮确定性纯Python整数计算。
使用1或4个context.map线程，任务/执行器CPU准入相应设置为1或4，其他配置相同。

| CPU向量步骤（三轮中位数） | 1线程 | 4线程 |
|---|---:|---:|
| embed步骤耗时 | 4.18 s | 1.24 s |

同一任务进程内的线程并行提速 **3.37倍**。这项实验包含真实
Python CPU工作，HTTP等待实验不能用于证明CPU并行。实际提升受CPU配额、业务依赖
线程安全性和C扩展的free-threading兼容性影响，框架在加载算子后再次检查GIL。

## 规模与内存补充

| 场景 | 结果 | 耗时 | 吞吐 |
|---|---|---:|---:|
| 24文件、2执行器×4槽位 | 24/24成功，24次尝试，使用2个执行器 | 2.25s | 10.69文件/s |
| 120文件、2执行器×8槽位，每文件2048字符 | 120/120成功，120次尝试 | 5.37s | 22.34文件/s |
| 单文件1048576字符、2185块、HTTP无额外等待 | 一次成功，校验全部向量产物与索引行数 | 1.62s | 1345块/s |

120文件与24文件大小不同，吞吐数值不能直接作为扩容倍率比较。
大文件任务进程峰值RSS **47.7MiB**，120文件中
单个任务的最大RSS为 **39.3MiB**，包含解释器，
不含管控、执行器父进程、外置模型或全部并发任务的内存。当前环境/proc中的管控
RSS不可可靠读取，所以标记null；没有据此宣称管控内存上限或生产系统不会OOM。

## 进度上报开销

10000次report的实测：基线 **10003次**持久写入、1.622s；
改进版 **3次**持久写入、0.0064s。内存中计数不丢，
步骤终态立即落盘；中间计数约100ms合并刷新。崩溃时最近未刷新计数可以丢失，
本版整文件重跑，不使用计数作为断点恢复依据。1000步大DAG和转义日志还验证了续租
JSON大小边界，避免诊断数据挤掉租约更新。

## 复现

在仓库根目录、安装3.14t与dev依赖后：

```bash
python scripts/benchmark_suite.py
pytest -q
```

基线复现需要完整Git历史（默认提交e1fe96e）；只运行当前版本：

```bash
python scripts/business_benchmark.py --workers 2 --output /tmp/business.json
python scripts/business_benchmark.py --files 120 --workers 2 --slots 8 --chars 2048 --output /tmp/batch.json
python scripts/business_benchmark.py --dsn "$DATAFLOW_TEST_DATABASE_URL" --output /tmp/postgres.json
```

仅使用专用测试数据库。脚本会创建/保留任务历史，在临时目录生成输入和索引，结束
后删除临时文件。生产不应用这些测试数据库记录当作实际业务。

原始记录位于 [benchmarks](benchmarks)，对比汇总为 [summary.json](benchmarks/summary.json)。
CI验证全部文件一次成功、无额外重试及索引/产物完整性，不设置机器无关的吞吐阈值。
生产容量需用真实文件、模型服务、RWX存储和目标数据库重测；本轮没有验证节点断电、
真实NPU推理、长时间稳定性、租户公平性或自动扩缩容。
